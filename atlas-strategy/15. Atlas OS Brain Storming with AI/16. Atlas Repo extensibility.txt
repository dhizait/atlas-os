The whole point of the `drivers/` + `batches/` pattern is: *new product = new driver, not a rewrite.*

### *HOW EXTENSIBILITY WORKS IN ATLAS OS*

#### *1. ADD A NEW PRODUCT = ADD 1 FOLDER*
Example: Ministry says "We need Agriculture Input Vouchers"

We don’t touch Core or Lending. We just add:
drivers/agriculture-vouchers/
├── api/              # FastAPI for voucher CRUD
├── db/migrations/    # voucher table
└── batches/          # issue_vouchers.py, redeem_vouchers.py, reconcile_suppliers.py
Then register it in `DRIVER_BATCH_MANIFEST.md` and the Workflow Engine picks it up.

2 weeks later: "We need Pension Payments" → add `drivers/pensions/`  
Same OS, new driver.

#### *2. REUSE THE KERNEL*
Every new driver automatically gets:
OS Service	You Get It For Free
**Auth**	Keycloak login, roles, MFA
**API Gateway**	`/api/agriculture/*` route auto-added
**Workflow Engine**	Schedule `agriculture.issue_vouchers` at 9am
**Event Ledger**	Every voucher issued = audit event
**Rules Engine**	"IF beneficiary GRIT Score < 50 THEN block voucher"
**Observability**	Logs, metrics, alerts in Grafana
**DB**	New schema `agriculture_vouchers` in same Postgres
No copy-paste. No new infra.

#### *3. DRIVER BATCHES = PLUG AND PLAY*
The `scripts/run_driver_batch.py core.interest_accrual` CLI doesn’t care what driver it is.

To add "Agriculture EOD":
# drivers/agriculture-vouchers/batches/eod_recon.py
def run(): ...
Then run: `python scripts/run_driver_batch.py agriculture.eod_recon`

The orchestrator will run it alongside Core EOD.

#### *4. CROSS-DRIVER EXTENSIBILITY*
This is the powerful part.

Because everything goes through the `Event Ledger` and `Rules Engine`:
Lending Driver fires: "LoanDisbursedEvent"
→ Compliance Driver hears it → runs AML check
→ Payments Driver hears it → sends money  
→ GRIT Driver hears it → updates beneficiary GRIT Score
So new products can hook into old products without code changes.

### *REAL WORLD EXAMPLES*
If Ministry wants...	We do...	Time
**New Loan Product**	Add rules in `lending-driver`, no new code	2 days
**New Scheme: Health Grants**	`drivers/health-grants/` + 3 batches	1 week
**New Payment Rail: ZimSwitch**	Add to `payments-driver/batches/zimswitch.py`	3 days
**New Country**	New DB schema + config. Same drivers	2 weeks
DHIS2, G2P, and Temenos do it this exact way.

### *THE ONLY RULE*
To stay extensible we must keep:
1.  *1 Driver = 1 Business Domain* - Never put "voucher logic" in Core
2.  *All comms via Events/APIs* - Drivers never call each other’s DB directly
3.  *Batches are stateless* - `run()` in, result out. OS handles scheduling

Break those 3 and we’re back to monolith hell.
