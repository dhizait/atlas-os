### *2. WHY THESE 4 "ARMS" FEEL LIKE KERNEL*
Batch Cut	Why It Feels "Kernel Level"	Why It’s NOT Core Kernel
**BATCH-07 Product Studio**	Every bank launches products on Day 1. It’s the main UX	If Studio crashes, money is still safe in Accounts Core. Like `apt` crashing doesn’t kill Linux

They are *"privileged modules"*. They live 1 inch above kernel and have special API access.

Unix analogy: `systemd`, `NetworkManager`, `X11`. Not in kernel source, but you need them to use Linux.

### *3. THE 3 RULES FOR "KERNEL-LEVEL ARMS"*

This is how we keep them safe but powerful:

1.  *Rule 1: Read/Write via Events Only*  
    Studio never does `UPDATE accounts SET balance`. It posts `AccountDebitedEvent` to BATCH-01. Kernel validates.
2.  *Rule 2: Can Be Hot-Swapped*  
    We can deploy v2 of ISO Driver on Tuesday without rebooting kernel. Like `modprobe -r iso && modprobe iso_v2`
3.  *Rule 3: Can Be Toggled Off*  
    BATCH-06 Toggle Engine can turn off Workflow Studio for a tenant. Kernel + Accounts still run.

That’s why we cut them from Week 1. They don’t block "boot".

### *WHY AA CAN’T BE AN "ARM"*

If we moved AA to 🟡 Arms layer, 2 problems:

1.  *Data Risk*: AA writes to Accounts Core BATCH-04. If AA crashes mid-write, GL is corrupt. Must be in vault.

It’s like the Linux process scheduler. Can’t be a user program.
